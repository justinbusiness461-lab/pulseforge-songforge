### Mission 043 candidate — 2.20.0

Lyrics are immutable metadata owned by the durable ProjectRevision, never browser
storage or a `latest lyrics.json` file. Save/open a project, choose a short PCM16 WAV,
enter known words, and use **Lyrics — guided speech fixture**. Correcting a word
creates a new lyric and project revision with the same audio and timing. Reopen by
project ID to restore the current lyric revision; open a historical project revision
through the API to retrieve its original lyrics. Stale writes return 409.

This first method is **provided-text energy-island alignment**, not ASR, singing
recognition, or automatic vocal detection. It requires one separated signal region
per supplied word; otherwise it returns `unknown` with no words. Confidence is
explicitly unknown (`null`), not an invented model probability. Text can be wrong;
energy alone cannot establish that audio contains speech. Supplying no transcript
never invents words, including on instrumental input. The retained spoken fixture
was generated by local Flite; timing references are signal construction bounds,
not perceptual/phoneme annotations. Continuous music/singing is outside this gate.

`POST /api/projects/lyrics` uses the existing origin/capability policy and requires
`projectId`, `expectedCurrentRevisionId`, and either:

- `action: candidate`, `sourceArtifactId`, `knownTranscript`, `language`; or
- `action: correct`, `expectedLyricRevisionId`, `changes: [{wordId,text}]`, `actor`, `reason`.

Audio SHA means decoded interleaved PCM16LE SHA-256; sample rate/channels/encoding
are bound separately. `sourceArtifactId` is the exact WAV-container SHA-256.
`revisionId` hashes canonical lyric JSON excluding its own revisionId;
`ProjectRevision.lyricTimelineDigest` hashes the complete stored lyric JSON.
`parentArtifactId` makes prior lyric/evidence/audio objects resolvable and durable.
No DSP or historical audio changes belong to this release.
